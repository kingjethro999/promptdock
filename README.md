# PromptDock

Turn a rough idea or spoken note into an editable prompt for ChatGPT, Claude, Gemini, and other AI tools. The app includes a public interactive landing page, a chat or classic workspace, templates, voice input, account-based library sync, public prompt and profile sharing, a community feed, bring-your-own-key settings, copy, and Markdown export. It installs as an app and shows a clear offline state.

## What the workspace does

**Two layouts, one builder.** `/workspace` has a **Chat / Classic** switch (remembered per browser). Chat asks clarifying questions inline, shows the finished prompt in a copy block, then explains it. Classic is the original two-pane layout. Both use the same store (`src/stores/prompt-builder.ts`), so a prompt shaped in one opens in the other.

**Explaining each result.** Every generated prompt comes with:

- _What changed and why_: a short list of upgrades, each with a reason.
- _Before and after_: an expandable panel (`PromptDiffPanel`) comparing the new prompt with what you wrote, or with the previous version when you revise one. Added words are highlighted, removed words are struck through, and the word counts before and after are shown. The comparison text is recorded as `baseline` when a result is accepted.
- _How to check the answer_: yes/no checks to run on what the target AI returns, with a button that copies them as a ready-to-paste checklist.

**Model arena.** **Compare** runs the finished prompt on several models. Under each answer, notes say what it adds that the others do not, how many of your checks it appears to cover, and when you would pick it. These are counted from the text (`src/lib/prompt/arena-insights.ts`); no AI judges the answers. If a provider is rate-limited or down, the next configured provider is tried so the comparison is not empty.

**The + menu in chat** adds files (images and text files, up to 10 per message; paste and drag also work), fine-tuning (tone, format, audience, what to avoid), and research and sources (web research on, off or automatic, and a page to read first). The microphone beside send records up to 10 minutes and sends on its own when time runs out. Selections elsewhere in the app use check-badge rows (`ChoiceCard`) instead of bare radio circles.

**Library.** A card's title and **Edit** open title, tags and text in place (saved as a new version, sharing unchanged). **Remix** takes the prompt to the workspace to reshape it.

**Community and profiles.** Cards in the community feed have one primary **Remix** action plus icon buttons for copy and save, and the grid sizes its columns to the space available. Every public profile has a **Share** button (the system share sheet where there is one, otherwise it copies the link), also reachable from Settings. Social previews use the person's name, for example "Alex invited you to follow them on PromptDock". A prompt link that cannot be opened (private, followers only, deleted or mistyped) shows one explanation that does not say which, so a private prompt's existence is never revealed. The same visual style covers the general 404 page.

**Installing and offline.** PromptDock is a Progressive Web App. `src/app/manifest.ts` starts the installed app at `/auth?source=pwa`; someone already signed in is sent straight to `/workspace`. `public/sw.js` serves `/offline.html` when a page cannot load and caches only content-hashed build assets; pages and `/api/*` always go to the network, so private data is never stored. While offline, a banner explains what waits for the connection and the chat send button is disabled. The service worker is served with `Cache-Control: no-cache`, and the content security policy allows `worker-src 'self'` and `manifest-src 'self'`. In development, bundles are never cached.

**Phones.** Modals become bottom sheets under 640px: they rise from the bottom edge, show a grabber, and can be swiped down to dismiss. Loading states use skeletons (`src/components/ui/Skeleton.tsx`) in the library, workspace, community and settings.

The App Router is the configured deployment. The previous UI is preserved in [`oldui/`](oldui/README.md) and runs with `npm run legacy:dev` for visual and behavior comparison. Both hosts call the same `src/backend.js` implementation for authentication, database, AI, sharing, referrals, and admin actions. Next.js adapts its Web request to that handler at `src/app/api/[...path]/route.ts`. See [the migration audit](docs/next-migration-audit.md) for verified parity and remaining work.

The UI and API deploy together as **one Vercel project**. The browser calls `/api/*` on the same site; no separate backend URL or CORS setting is needed. API keys and `DATABASE_URL` belong in Vercel's server-side environment variables, never in the browser build.

Guests and signed-in users can choose **Send feedback** on the landing page or **Report an issue or idea** in the workspace sidebar. Reports are saved in PostgreSQL's `feedback_reports` table with a type, message, and optional reply email. The API accepts up to five reports per hour per account or guest IP. The administrator can read submissions at `/admin`; the server also emails each report to `ADMIN_EMAIL` through the configured Gmail SMTP account. If SMTP fails, the saved report remains in the admin inbox. Do not put private details or provider keys in a report.

The signed-in account whose email matches `ADMIN_EMAIL` can open the **Admin console** link in Settings. The console shows aggregate site counts and submitted feedback, and can publish or remove product updates. It does not expose users' private prompts or original idea inputs. `ADMIN_EMAIL` defaults to `king18jsquare@gmail.com`; set it explicitly in Vercel if the administrator address changes. Admin AI and voice usage is unlimited, while unauthenticated sign-in attempts remain rate limited.

## Run locally

Requires Node.js 20.19+ — that is the floor in `package.json` `engines`, and the lowest release ESLint accepts. The test suite adds one more constraint: the jsdom DOM tests need Node 22.22+ or 24.15+, and GitHub Actions runs Node 24. Copy `.env.example` to `.env` and set a provider key for AI features. The manual builder works without one.

```bash
pnpm install
pnpm dev
```

pnpm is the primary package manager (`pnpm-lock.yaml`). `package-lock.json` is kept in step because the GitHub Actions workflow installs with `npm ci`.

Open <http://localhost:3000>. `npm run dev` starts the Next.js App Router with hot reload. Run `pnpm build && pnpm start` to serve its production build locally. Set `DATABASE_URL`, `GMAIL_USER`, `GMAIL_APP_PASSWORD`, and `BYOK_ENCRYPTION_KEY` in `.env` to use all account features locally. Next.js loads the ignored `.env` file. The landing page is public; verified users open directly into the workspace.

To compare both UIs, run `npm run legacy:dev` on port 3000 and `npm run next:dev -- -p 3333` on port 3333 in separate terminals. They share the backend implementation and need the same database and server environment variables for account journeys.

Create an account, verify the link sent by email, and sign in to sync prompts across devices. Sign-up asks for a username — 3–24 letters, numbers, or underscores, unique across accounts — that travels with everything you share; Settings can change it later. Both forms show format and availability feedback while typing, then check again on submission; the database uniqueness constraint remains the final guard against simultaneous claims. The workspace header shows your username when you have one, or your email for older accounts without a username. Password fields carry a **Show**/**Hide** toggle so you can check what you typed. The account flow includes password reset, password change, and signing out on all devices. Passwords are hashed with scrypt; sessions use HTTP-only cookies. Verification links expire after 24 hours and reset links after 1 hour. Settings lists your active sessions with their device and sign-in time so you can end one you do not recognize, and **Delete account** erases your prompts, revisions, saved provider keys, and every session once you confirm your password. The first sign-in in a browser imports prompts saved by older PromptDock versions, including their tags and save dates, then removes the old browser workspace token.

Saved prompts can have up to eight tags. Library search runs on the server across names, ideas, tasks, and tags; results load in pages of 100 so older prompts remain searchable beyond the first screen. The library shows your tags as clickable filter chips with their counts; selecting a chip (or clearing it) filters server-side through `tag=`, and the sort control switches the order between recently updated and name A–Z (`sort=`), both for signed-in accounts and for prompts stored in the browser.
Every changed save keeps the previous version in a prompt's **History**. The 10 most recent earlier versions can be restored, and a restore keeps the current version in history too. **Compare** previews a version against your current prompt first, showing changed fields line by line with the lines a restore would remove or bring back, so nothing is restored blind. Deleting a prompt removes its revisions.
Use **Duplicate** on any library card to create a private, independent copy with its idea, notes, fields, and tags.
**Export JSON** downloads the entire library in one server request, including prompts beyond the first search page, and keeps each prompt's id, save time, tags, and fork origin. **Import JSON** adds private copies from a PromptDock backup; an id or fork origin that is still free in your library is reused, anything already there gets a fresh one, and save times are kept so your sort order survives a restore. Public links and account details are not exported or restored.
**Paste in**, beside **New prompt**, opens a form for a title, prompt text, and optional tags so a prompt written elsewhere can be stored and shared without rebuilding its fields. Pasted text stays verbatim when copied, run, or viewed through a public link; adding builder fields turns it into a structured prompt. Workspace dropdowns use custom controls throughout, including library sorting and provider settings. Long menus offer a search box that filters as you type. Drafts, ideas, and prompts accept very long text: the remaining ceilings are safety limits counted in hundreds of thousands of characters, not a few thousand.

In **Idea to prompt**, users can start with a rough thought, a spoken idea, or an existing draft prompt. The preview labels unshaped text as a draft. **Fine-tune your prompt** stays collapsed and optional; users who know their desired role, audience, context, format, tone, approach, priorities, depth, or requirements can add them before generation. Only details the user chose travel with the idea in the same `/api/idea-to-prompt` request. Leaving the section untouched lets AI infer the structure. When a wrong assumption would materially change the result, PromptDock asks up to four focused questions together before generation. Clear ideas proceed directly. Answers remain with the original idea in the final AI request, and text-only question state survives a page refresh. Image attachments stay in the current page and must be added again after a refresh. The action button sits after the optional section. After generation, the preview identifies the finished prompt, and users can copy, run, save, or refine it. Changing the source clears stale questions or generated content while keeping user-chosen fine-tune details. Users can also attach up to ten JPEG, PNG, or WebP images, up to 25 MB each (in chat, other image types are converted, and text files are sent as text). The browser prepares large originals automatically to fit the hosting request limit; image quality may be reduced when several large images are attached. Images go to the selected AI provider during generation and any clarification round; the resulting prompt is self-contained text, and image bytes are not saved to the library. Groq switches to its configured vision model automatically; Gemini and Anthropic use their selected model unless a separate vision model is configured. APMIX and custom OpenAI-compatible providers need an image model ID in Settings.

To share a prompt, save it to **My library**, then choose **Publish & share** on its card. Anyone with the `/p/<id>` link can view and copy the finished prompt without signing in. Shared pages render prompt-specific Open Graph and Twitter metadata on the server, so link previews do not depend on JavaScript. When the owner has a name, the link preview is titled `<name> shared a prompt with you: <prompt name>` and the page title is the prompt's name; a prompt that cannot be opened shows the unavailable page described above. The public API exposes the prompt name and fields, but not the account email, original idea, or analysis notes. A guest who chooses **Save to my library** is taken through signup or sign-in; PromptDock creates an independent private copy. Repeating the action returns the same copy. **Make private** disables the old link while existing copies remain in their owners' libraries. Review prompt fields before publishing because the full finished prompt is public.

**Invite friends** in the sidebar shares PromptDock itself. Each signed-in account gets a stable `/invite/<code>` link; its public landing page has a personalized title and server-rendered Open Graph/Twitter metadata for social previews. The link never exposes the inviter's email. New accounts opened through the link remember the code through signup, and the inviter receives credit only after the new account verifies its email. The dialog shows verified and pending friends. Each of the first five verified referrals adds two hourly idea, run, and legacy fine-tune requests plus one hourly voice transcription; the maximum allowances are 30/30/40/15 respectively. The bonus is attached to the account and appears in the Settings usage meter. Deleted referral accounts no longer count toward the bonus. The Help button in the workspace now opens topic-based guidance for creation, the library, sharing, and settings, with direct actions to each area.

Prompt generation follows the source-backed design notes in [`docs/prompt-research.md`](docs/prompt-research.md). It preserves the user's requested action, separates instructions from idea input, gives concise examples to the model, and uses Gemini's system instruction field when Gemini is the provider.

**Run prompt** sends the assembled prompt to your configured provider and shows the reply in the preview column, so a draft can be tested without leaving PromptDock. The response can be copied or dismissed, and runs count against the same AI budget as generation: 20 per hour.

In Settings, save as many providers as you like — Anthropic, OpenAI, Groq, APMIX, Gemini, or a custom OpenAI-compatible or Anthropic-compatible endpoint — give each one a name, and choose the active entry from the **Active provider** dropdown; **PromptDock default** switches back to the system AI without deleting anything. Custom endpoints need a base URL that is HTTPS (localhost may use HTTP), and PromptDock appends `/chat/completions` or `/v1/messages` for you, so paste a root such as `https://openrouter.ai/api/v1`. APMIX BYOK uses `https://api.apmix.ai/v1` unless `APMIX_BASE_URL` is configured on the server. PromptDock's own APMIX key selects an available `-free` model from `/v1/models`, preferring `APMIX_MODEL` when that model is available to the key. BYOK keeps the user's chosen model. Keys are encrypted with AES-256-GCM before being stored in PostgreSQL. The API never returns the saved key. Set one stable `BYOK_ENCRYPTION_KEY` (64 hex characters) on every deployment; changing or losing it makes previously saved keys unreadable. Accounts keep up to 10 saved providers, one active at a time, and each can be renamed, updated, or deleted. The same two custom types can also be configured once for the whole deployment with the `OPENAI_*` and `ANTHROPIC_*` variables in `.env.example`. An active Groq key also powers voice transcription; otherwise the server's `GROQ_API_KEY` does.

Settings also carries a **This hour** usage meter for each current AI action — Run prompt, Idea to prompt, and Voice transcription. Every action draws from a rolling hourly budget shared by your account (or your IP when signed out), and `GET /api/usage` reports how many uses are left and when the budget refills, including any earned referral bonus, so the meter shows the cost of a busy hour before you hit a 429.

To dictate an idea, choose **Record idea**, speak, then **Stop & send**. The server transcribes with Groq and sends the resulting idea through prompt generation. **Cancel** discards the recording. In chat, the microphone records up to ten minutes and sends the transcript on its own at the limit; recordings are compressed so ten minutes stays under the 4 MB cap. Vercel's function payload limit caps uploads at 4 MB.

Run `pnpm test` for route, account, provider, voice, sharing, database validation, version, and browser DOM checks. The DOM tests load the real workspace page with jsdom and drive library search, tag chips, backup import, the paste-in form, searchable dropdowns, password show/hide toggles, and the username signup field, so no browser or server is required. The account flow test uses an in-memory query adapter, so it does not send email or require a live database.
Run `pnpm lint` to check the browser and Node code with ESLint. GitHub Actions runs `npm ci`, formatting, lint, security-header checks, tests, TypeScript, the existing frontend build, and the Next.js build on every push and pull request.

AI routes use a shared PostgreSQL token bucket to control provider spend across Vercel function instances: 20 idea requests, 20 test runs, and 10 voice transcriptions per hour, replenished gradually. An idea that needs clarification uses one idea request to ask questions and another to generate the final prompt. The older `/api/enhance` endpoint remains available to existing API clients with its own 30-per-hour limit, but the workspace uses the single idea-to-prompt flow. Buckets are keyed per signed-in account, so a shared office or mobile IP never spends another user's allowance; guests and sign-in attempts fall back to the client IP. Sign-in, sign-up, and email routes are throttled too: 20 logins and 10 password resets per 15 minutes, 10 sign-ups per hour, and 6 verification or reset emails per hour. Exceeding a limit returns HTTP 429 with `Retry-After`. Local development without PostgreSQL uses a process-local bucket. Bucket rows and stale local entries are pruned automatically once they outlive the longest limit window.

The Next.js proxy sets a nonce-based content security policy, frame protection, referrer policy, permissions policy, MIME sniffing protection, and HSTS for page responses. The existing API handler applies its own equivalent security headers. `pnpm headers:check` verifies the Next.js deployment configuration and the proxy's required headers.

The repository guards against injected payloads: `pnpm payload:check` (also a pre-commit step and the first CI job, run before anything installs) refuses obfuscated code hidden after long runs of whitespace, a root-level `init` loader, package scripts that run it, editor tasks that execute on folder open, and a `.gitignore` that stops ignoring `.env`.

## Deploy

1. Import this repository into Vercel. Keep **Root Directory** as `./` and use the **Next.js** framework preset. The repository's `vercel.json` declares `nextjs` and pins the output directory to `.next`, overriding any old `src/dist` project setting. Use the default Next.js build command. Set **Install Command** to `npm ci` if you override Vercel's default.
2. Add server-side environment variables in Vercel: `DATABASE_URL` (your Render database's **External URL**), `GMAIL_USER`, `GMAIL_APP_PASSWORD`, `ADMIN_EMAIL` (the administrator's account email), and `BYOK_ENCRYPTION_KEY` (64 hex characters). Add `GROQ_API_KEY` and `GROQ_MODEL=openai/gpt-oss-120b` for PromptDock's default AI and voice, or configure another provider from `.env.example`. Profile photos and covers upload to Cloudinary: set `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and `CLOUDINARY_SECRET` (`CLOUDINARY_API_SECRET` or a single `CLOUDINARY_URL` also work). Without them, signup still completes and photo upload says it is switched off. Keep all secret values out of Git and the browser build.
3. Deploy. The server uses verified TLS for Render external URLs and creates or migrates account, session, token, settings, and prompt tables on first database access. Open `/api/health` on the Vercel domain and expect `{"ok":true}`.
4. Once the permanent Vercel or custom domain is known, set `APP_URL` to that full HTTPS origin and redeploy. Verification and reset emails, canonical URLs, social previews, `robots.txt`, and the sitemap all use that address. Without `APP_URL`, they use Vercel's production URL when available, then its deployment URL.

Search crawlers get a canonical link, Open Graph and Twitter card previews, and schema.org structured data on public pages, plus `robots.txt`, `sitemap.xml`, and a factual `llms.txt` at the domain root. The homepage uses `public/social-card-v2.png` as its large social preview; legal and update pages use the original social card. The landing page includes visible product answers and links to [PromptDock on TikTok](https://www.tiktok.com/@thepromptdock) and the source repository. These changes help crawlers and AI search systems understand the product, but do not guarantee a particular search result or AI citation. [Google's AI feature guidance](https://developers.google.com/search/docs/appearance/ai-features) says ordinary SEO fundamentals still apply. Updates are published as an RSS feed at `/feed.xml`, which Next.js metadata advertises through `rel="alternate"`. Sign-in, admin, invitation, and empty shared-prompt pages carry `noindex`; duplicate `/*.html` URLs redirect to their clean paths through Next.js redirects.

The provider keys, Gmail app password, encryption key, and database URL are never written to Git or the static frontend. The root `.env` is ignored by Git. Voice uses a browser with `MediaRecorder` on localhost or HTTPS.

Render Free Postgres has a 1 GB limit and expires after 30 days; plan an upgrade or export before expiry if you need to keep the data.

## Versioning

The project began at `v0.0.1`. The pre-commit hook bumps every later commit: `v0.0.9 → v0.1.0`, then `v0.1.0 → v0.1.1` and so on. Each `0.x.9` rolls to `0.(x+1).0` through `v0.598.9 → v0.599.0`; the final pre-1.0 sequence is `v0.599.0` through `v0.599.9 → v1.0.0`. From `v1.0.0` onward, commits increment the patch number. `package.json` uses numeric SemVer; `VERSION` and the frontend build use the `v` prefix. Run `npm run setup:hooks` after cloning. The hook runs `npm run lint` first, so a commit that fails lint is rejected before the version moves on; when `node_modules` is missing it warns and skips the lint step instead.
